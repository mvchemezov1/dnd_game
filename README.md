# ⚔️ Dnd_game – Backend для D&D-подобной RPG  

**Event Sourcing + CQRS + .NET 8** – мощный движок для многопользовательских ролевых игр.

---

## 🎯 Что это?

Это **бэкенд-сервер**, который управляет игровым миром, персонажами, диалогами, крафтингом, торговлей и событиями в реальном времени. В основе лежит **Event Sourcing** – каждое действие игрока сохраняется как неизменяемое событие, что позволяет перематывать историю, откатывать состояния и строить любые проекции для аналитики.

Проект реализует **CQRS** (разделение команд и запросов) и **Domain-Driven Design**, что делает код чистым, тестируемым и масштабируемым.

## 🚀 Ключевые возможности

| Функция | Описание |
|---------|----------|
| 📦 **Event Store** | Хранилище событий и снапшотов в PostgreSQL |
| 🔄 **CQRS + Проекции** | Чтение и запись разделены, проекции строятся асинхронно |
| 🛡️ **Consistency Manager** | Контроль версий, оптимистичные блокировки, разрешение конфликтов |
| 📬 **Обработчики** | Триггеры, вебхуки, крафтинг, диалоги, торговля, скриптовый движок |
| 🔐 **JWT + RBAC** | Безопасная аутентификация и политики доступа |
| 💬 **WebSockets** | Реал-тайм взаимодействие (чат, уведомления, обновления состояния) |
| 🐰 **RabbitMQ** | Асинхронная обработка фоновых задач (опционально) |
| 🧪 **In-Memory репозитории** | Быстрая разработка и тестирование без БД |

## ⚙️ Быстрый старт

```bash
# Клонировать репозиторий
git clone https://github.com/ваш-аккаунт/dnd_game.git

# Перейти в папку
cd dnd_game

# Восстановить пакеты
dotnet restore

# Запустить PostgreSQL и RabbitMQ через Docker (или вручную)
docker run -d --name postgres -e POSTGRES_PASSWORD=pass -p 5432:5432 postgres
docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:3-management

# Задать секрет для подписи JWT (обязательно — без него приложение не стартует, см. ниже)
dotnet user-secrets set "Token:Secret" "<любая длинная случайная строка>"

# Применить миграции (если есть) или запустить инициализацию БД
dotnet run
```

После запуска сервер будет доступен по адресу `http://localhost:5000` (или порту из конфигурации).

### 🔑 Секрет JWT

`Token:Secret` (используется для подписи access/refresh токенов) **не хранится в
`appsettings.json`** — приложение намеренно падает при старте, если он не задан или
остался плейсхолдером, чтобы никто случайно не запустил его с общеизвестным ключом.
Как задать:

- **Локально**: `dotnet user-secrets set "Token:Secret" "<значение>"` (секрет хранится
  вне репозитория, в профиле пользователя — `UserSecretsId` уже настроен в
  `dnd_game.csproj`).
- **Docker Compose**: переменная окружения `TOKEN_SECRET` (см. `docker-compose.yml`) —
  по умолчанию подставляется заведомо небезопасное значение только для локальных
  запусков; для чего-то похожего на прод переопределите её.
- **Прод/CI**: переменная окружения `Token__Secret` (двойное подчёркивание — стандартный
  для ASP.NET Core способ адресовать вложенный ключ конфигурации).

### 🧪 Тесты

```bash
# Юнит-тесты (не требуют БД)
dotnet test tests/dnd_game.Tests.csproj --filter "FullyQualifiedName~Tests.Unit"

# Интеграционные тесты Event Store (требуют реальный PostgreSQL)
export DND_TEST_POSTGRES_CONNECTION="Host=localhost;Database=dnd_test;Username=postgres;Password=pass"
dotnet test tests/dnd_game.Tests.csproj --filter "FullyQualifiedName~Tests.Integration"
```

Без `DND_TEST_POSTGRES_CONNECTION` интеграционные тесты тихо пропускаются (не падают) —
подробности в комментариях `tests/integration/PostgresEventStoreTests.cs`.

### 📊 Нагрузочный тест Event Store

Проверяет запись и чтение через `PostgresEventStore` на целевом профиле нагрузки —
50–500 одновременных активных боёв, смешанный сценарий (запись действий + чтение
состояния "зрителями"), а не абстрактные цифры. Подробности профиля — в комментариях
`tests/loadtest/Program.cs`.

```bash
# ВАЖНО: используйте отдельную тестовую БД — тест пишет реальные события и не чистит их
export DND_LOADTEST_POSTGRES_CONNECTION="Host=localhost;Database=dnd_loadtest;Username=postgres;Password=postgres"
dotnet run --project tests/loadtest -c Release -- --levels 50,200,500
```

На выходе — сводная таблица с p50/p95/p99 задержки записи и чтения на каждом уровне
нагрузки. Решение о добавлении кеша (Redis) для горячих проекций стоит принимать по
этим цифрам: если на уровне 500 p95/p99 выходит за приемлемый для вас порог отклика —
это сигнал добавлять кеш; если нет — пока не нужен.
